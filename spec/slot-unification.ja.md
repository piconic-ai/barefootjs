# ハイドレーション設計 — あるべき姿（日本語概説）

正式な規範文書は英語版 [`slot-unification.md`](./slot-unification.md) です。
本書はその「あるべき姿」だけを平易に述べる概説で、両者が食い違う場合は英語版が優先します。
節番号（§n）は英語版の節を指します。

## 全体は4つの規則から導かれる

設計判断に迷ったら、個々の節ではなくこの4つに照らします。

### 1. 位置は一度だけ解決する

要素の住所は claim 時に決めて、参照として保持する。更新のたびに DOM を
走査し直さない。

- 根拠: 更新コストを「変わった箇所の数」に比例させるため。走査を許すと
  コストが「文書の大きさ」に比例してしまう。
- 施行箇所: §2 の claim-once 規則。実装は `claim-slots.ts` の単一の
  `claimRefs`（3つのアクセサ束 `claimSlots` / `lazySlots` /
  `lazyClaimSlots` は解決方法の分岐ではなく、行ごとの割り当て量の分岐）。

### 2. 組み立てと初期化を分ける

文字列を組み終えてから DOM ノードにし、DOM に接続してから `init` を
走らせる。組み立ての途中で DOM ノードを作らない。

- 根拠: `useContext` などの位置依存の解決は、要素が木に繋がって初めて
  正しく答えられる。接続前に `init` を走らせると「どの提供元を掴むか」が
  実行順の偶然で決まる。
- 実行順は5段で、順序そのものが要件:
  1. 文字列を組む
  2. 子は「文字列 + 後で走らせる `init`」で返す —— **未実装のまま §7 の
     Non-goal**（担うはずだった問題は `__bfSlot` と構造化 IR で解決済み）
  3. 全体を DOM ノードにする
  4. DOM に接続する
  5. `init` を走らせる
- 段4・5 は3経路（子スロット / `createComponent` 根の行 / テンプレート
  clone 根の行）すべてで成立済み。

### 3. 子位置は実行時に判別する

スロットに入る値が DOM ノードなら identity のまま退避・移動し、文字列なら
エスケープして書く。**エスケープが既定**で、raw 出力は明示した場合だけ。

- 根拠: 「JS テキストと JSX の混在物」を番兵付き文字列で運ぶと、規約を
  知らない出力先が1つあるだけで silent leak になる（CLAUDE.md の
  write-side 規則）。値の種別は型ではなく実行時の値で判別する。
- 施行箇所: `__bfSlot` と構造化 IR（`MapCallbackPreamble` など）、
  単一の描画扉 `renderPreamble`。

### 4. 行は資源を持たない

ループの各行に reactive 資源（effect・購読・クロージャ）を作らない。
コストは「更新された行の数」にだけ比例させる。

- 根拠: 1k 行のリストで行ごとに effect を張ると、作成時のヒープと
  ハイドレーション時間が行数に比例して膨らむ。実測でこの規則の有無が
  solid 比 29% のメモリ差になった。
- 施行箇所: §9 の lazy row graph。適格性判定（§9.4）は満たせないとき
  **eager 出力へフォールバック**する —— 健全性を落とす方向には決して
  倒れない。

## 規則を破ってよい場所は無い、緩めてよい拒否も無い

英語版が「緩めるな」と明記している拒否は4つ（ループ元データの由来が
証明できない / プロファイルモード / key の無いループ / 識別子集合が
取れない束縛）。これらは backlog ではなく設計の一部です。
