A callback parameter or local named like the component's props object (`props`) now keeps its own binding in the client JS. The client JS reads the component's props through `_p`, and the rename of `props` to `_p` used to also rename every inner binding spelled `props`. That covered a `.map((props) => …)` row, a handler's `(props) => …` arrow, a `.filter((props) => …)` callback, and a nested `function f(props)`. The renamed parameter then captured the outer prop reads inside it. In a component with destructured props, a row created on the client rendered `undefined` for an outer prop (`{suffix}`), and a child prop forwarded from the row lost its value. A handler such as `(props) => setN(n() + props.by * step)` produced `NaN`. Only references that resolve to the component's props are renamed now. A `var` declared in a nested block or a `for (var …)` head binds in its whole function, as in JS: a read after the block is that local, both for a `var props` and for a `var` named like a destructured prop, which the client JS used to rewrite to the prop (`if (c) { var step = 5 } setN(step)` read `_p.step`). One gap remains and is recorded as a limitation: on the template adapters other than Hono and Go (Blade, erb, Jinja, MiniJinja, Mojolicious, Pebble, Twig and Xslate), a server-rendered row whose parameter is named `props` renders `props.label` as the component prop `label` (`loop-param-named-props-member`).
