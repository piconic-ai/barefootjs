A local function, const or module binding that shares its name with a typed prop of a `(props)`-arg component keeps its lexical meaning on SSR (#3721). Before, every template adapter read `value()` (with `function value() { return 1 }` and `props: { value?: number }`) as the prop, so a supplied `{ value: 9 }` rendered `9` where Hono renders `1`. The SSR seed plan and the static SSR defaults now treat a prop as a bare name only where the component binds it (`templatePropReadParams`, the decision the client template already used). A zero-argument call of a function that takes no parameters and returns one expression (a `function` declaration or an arrow `const`, component or module scope) now renders as that expression in markup, memo bodies and signal seeds. A zero-argument call of any other local function is refused with BF101 instead of rendering an unbound name or the prop, in markup and wherever the server render reads it through a memo body or a signal seed (a read deferred with `/* @client */` is not refused). Each such call is resolved lexically: a component declaration of a name hides the module one whether or not a template can inline it, a module function's body reads the module's bindings beside a component binding of the same name, and the BF101 refusal follows what a server-rendered position reads through const initializers and inlined functions, with loop rows and callback params shadowing as in JS.
