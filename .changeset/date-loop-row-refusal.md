A catalogued `Date` call on a `.map()` row (`rows.map(r => r.at.getUTCFullYear())`) is still refused with BF021. The message now says that the receiver is read through the loop row binding and that the Date lowering only resolves receivers read through props. Before, it claimed the method has no catalogued lowering. The loop-row message is used only when the same call would lower on a `Date` prop: a `toLocaleDateString` without an explicit literal `timeZone` keeps the uncatalogued message. For any call read through a loop row, the suggestion offers only the escapes that work on a row: a pre-computed per-row field, or a `/* @client */` revival of the row field for `Date` and `URL`. It no longer suggests adding a literal `timeZone` or passing the value as a prop, which only compile a prop's call. When the row field's type is unknown (it may come from a base type that is not declared in the file), only the per-row field is suggested, because a `new Date(...)` revival is wrong if the field is not a `Date`. For a receiver read through `?.`, the suggestion asks you to keep the null guard instead of offering an unguarded `new Date(...)` rewrite. A destructured row (`rows.map(({ at }) => at.getUTCFullYear())`) is refused the same way; before, it reached the template adapters as a plain method call on the row field.
