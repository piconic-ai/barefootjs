Fix #2897: a reactive conditional (`{cond ? A : B}`) inside a static (non-signal) array's `.map()` row — either the row's own content or a depth-1 nested loop's row — never wired up reactively on the client. Neither the static `forEach` bake nor the `inner-loop-nested` clone-and-wire architecture (#2798) has any conditional-handling machinery, so the branch silently froze at its SSR-time value and never updated again. The client-side loop-routing decision now falls through to the plain/composite dynamic path (the same machinery a signal-backed array already uses correctly for this shape) whenever a conditional is present anywhere in the row tree; a row with only ref/reactive-text/reactive-attr bindings and no conditional keeps taking the static fast path unchanged.

Follow-up fix: narrow that escalation to conditions that can actually change after first render. `classifyReactivity` reports any loop-param-referencing condition (e.g. `item.key === 'messages'`) the same way it reports a signal read — array static-ness plays no part in that classification, by design — so the escalation above was firing for a static array's row conditional even when the condition read only the (for a static array, fixed-forever) loop item, regardless of whether the branches were a bare element or a child component. That over-escalation moved such rows onto the composite `insert()` path unnecessarily, which double-mounted a child-component branch on hydration. The escalation now checks a new `reactiveBeyondLoopScope` flag — computed independently of `classifyReactivity`'s loop-param-first precedence — so only a condition that itself reads a signal/memo/prop/preamble-reactive local escalates; an item/index-only condition stays on the static path, exactly as bakeable as it always was.
