The client JS no longer substitutes a value into a position that writes a binding. A destructured prop the component writes (`function C({ start = 0 }) { const add = () => setItems([...items(), ++start]) }`, or `start += 1`, `start = clamp(start)`, `[a, b] = [b, a]`, `for (k in o)`) used to have every reference rewritten into the live prop read, so the write became `++(_p.start ?? 0)`, a SyntaxError that broke the whole client module; a prop without a default wrote into the props object instead (`++_p.start`). Such a prop is now a local, as in JS: the init body declares it once (`let start = _p.start ?? 0`) and reads and writes that local, like the body form `let { start = 0 } = props`. A markup expression that writes a component-scope `let` during render (`{++nextId}`, a counter a `.map()` row increments, a child prop `get={() => ++nextId}`) no longer inlines the declared value into the client template (`++(0)`); the template leaves the slot, or the child, to init. The same holds for a memo body that writes a local. A `let` written only by event handlers still renders its declared value in the client template. A `for (let i …)` head inside a handler now shadows a prop of the same name, where its `i++` used to become `(_p.i ?? 5)++`.
