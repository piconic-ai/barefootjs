The client JS no longer substitutes a value into a position that writes a binding. A destructured prop the component writes (`function C({ start = 0 }) { const add = () => setItems([...items(), ++start]) }`, or `start += 1`, `start = clamp(start)`, `[a, b] = [b, a]`, `for (k in o)`) used to have every reference rewritten into the live prop read, so the write became `++(_p.start ?? 0)`, a SyntaxError that broke the whole client module; a prop without a default wrote into the props object instead (`++_p.start`). Such a prop is now a local, as in JS: the init body declares it once (`let start = _p.start ?? 0`) and reads and writes that local, like the body form `let { start = 0 } = props`. A `'use client'` component whose markup writes a component binding while it renders (`{++nextId}`, a counter a `.map()` row increments, a callback a call there may run in place such as `Array.from(xs, () => ++nextId)`) is now refused with BF065, where it used to inline the declared value into the client template (`++(0)`): no client path can keep the written value. A write under an event-handler attribute, wrapped or not (`onClick={wrap(() => nextId++)}`), in a function handed on as a value (a child prop such as `get={() => ++nextId}`, a context value's setter) or in a statement before the `return` is unaffected; a child whose prop writes a binding renders in init instead of the client template. A memo body, or a const whose initializer writes a binding (`const label = ++start`), is no longer inlined into the client template either; init runs it once and fills the slot. A `let` written only by event handlers still renders its declared value in the client template. A `for (let i …)` head inside a handler now shadows a prop of the same name, where its `i++` used to become `(_p.i ?? 5)++`.
