A `.map()` over an array prop whose row is a child component with no forwarded children (`props.items.map(item => <Badge key={item.id} label={item.label} />)`) now keys each row by the source row, as Hono does. Before, the generated `NewXxxProps` read the key off each row's `<Child>Input`, so a key field the child takes no prop for failed to build (`BadgeInput has no field or method ID`), a same-named child prop passed a different field set `data-key` from that prop (`key={item.id} id={item.slug}` rendered `data-key` from `slug`), and a scalar row's own value (`names.map(n => <Mark key={n} label={n} />)`) rendered no `data-key` at all. `NewXxxProps` now builds these rows from the array prop's own `Input` field (`in.Items`, `in.Names`), each child's props and its `data-key` read off the row. The `Input` struct no longer has the `<Child>s []<Child>Input` field for such a loop, so Go code that set it no longer compiles; pass the array prop instead. A loop whose child props can't be read off the row (a computed value, a field the row's Go type lacks, or a row value whose Go type isn't the child field's own, such as a whole row or an object field passed to an object-shaped prop) keeps the caller-supplied `<Child>s` rows, and takes its `data-key` only from a declared child prop passed the same row read as the key (a rest-bag attribute doesn't count); a row-read key no child prop carries is now refused with BF101 instead of failing to build or rendering the wrong key. One shared `loopKeyToGoRowExpr` (`lib/loop-row-path.ts`) now answers the key for every constructor path that ranges over source rows, including a scalar row keyed by its own value.
