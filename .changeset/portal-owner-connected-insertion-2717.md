Fix #2717: `createPortal` now moves its content to the container's end once the `ownerScope` is connected to the document. Hydration is unchanged (the owner is already in the document when `init` runs, so the single synchronous append stays as it was), but a client-side mount used to portal BEFORE the root was connected — `materializeComponent` runs `init`, and so the `ref` callbacks that call `createPortal`, before a bare `createComponent()` caller appends the result — leaving `document.body` as `[…portals, root]` where hydration produces `[root, …portals]`. Child order is user-visible (paint order between equal-`z-index` overlays, focus traversal, `querySelector` results), so both paths now converge on the hydration answer. The append itself is never deferred: the element is appended at call time exactly as before, so a `ref` callback that measures it synchronously (`offsetWidth`, `getBoundingClientRect()` — every floating-position component does this in its first effect run) still sees a live, laid-out element; a portal whose owner is still detached is then re-appended (moved to the end) once the owner connects, via a `MutationObserver` that lives only while something is pending, in creation order and before the next paint. A child component whose own root is the owner (`ownerScope === element`) waits on the tree it was taken from instead. The reorder itself prefers `Element.moveBefore()` when the environment supports it, falling back to `appendChild` otherwise — `moveBefore` moves an already-connected node without `appendChild`/`insertBefore`'s side effects on one (resetting `<iframe>` load state, `<video>`/`<audio>` playback, CSS animation state, and focus). Graduates the `idempotence` quarantine rows for the `dialog`, `dropdown-menu`, `popover` and `portal` oracle fixtures.
