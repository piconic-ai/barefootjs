Fix #2867/#2830: `shouldAutoDeferReactiveBrand` (the auto-defer check for a brand-package reactive read in a JSX conditional or attribute, #1638) used to stringify its whole candidate expression to regex-test it for a native signal/memo call. For a `.map()` loop or a ternary/`&&` with JSX arms, that expression is JSX-bearing — whenever the TypeChecker was active and resolved a `Reactive<T>` brand anywhere in the expression, this tripped the compiler's `getJS()` trust-boundary assertion (armed by the `map-body-no-silent-divergence.test.ts` harness) with an uncaught exception instead of a normal compile. This reproduced deterministically whenever `@barefootjs/client`'s `dist` was built and the checker resolved the brand — which looked like an environment-dependent flake (#2867) rather than the actual compiler bug it was (also reported separately as #2830).

Fixed two things: `jsx-to-ir.ts`'s `transformExpressionInner` now checks `ir.type === 'conditional'` before calling `shouldAutoDeferReactiveBrand` at all (it only matters for conditionals; calling it for every `.map()`/element/component was both wasted checker work and the trigger for the crash), and `shouldAutoDeferReactiveBrand` itself now reads only the brand-carrying leaf node(s) of the expression (via a new `collectReactiveBrandLeaves` in `reactivity-checker.ts`) instead of the whole expression, so it's safe even for a genuinely JSX-bearing conditional. Also tightened the `getJS()` trust-boundary assertion's gate (`analyzer-context.ts`) to ignore `warning`-severity diagnostics (e.g. BF043 props-destructuring) so it isn't silently disarmed by them — only an `error`-severity diagnostic does that, as intended.
