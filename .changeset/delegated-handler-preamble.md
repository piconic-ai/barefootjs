Fix delegated event handlers for keyed `.map()` loops whose body has an array-builder preamble (`const cells = []; cells.push(<span>...)`) plus a row-level event handler — every delegated action used to throw `t is not a function`. The delegation-context preamble's JSX leaf was rendered with the same loopParams accessor-wrap used for the mapArray row-render context, where the item genuinely is a signal accessor; in the delegated handler the item is the plain object `.find()`/index lookup returns, so the rewrite produced invalid `t().name` calls. The preamble leaf now renders in plain-object form, is only spliced into a given event's handler when that handler actually references one of the preamble's declared names (an unused array builder like `cells` above is no longer spliced at all), and — when spliced — always runs inside the item-null guard so a stale-DOM `.find()`/index miss short-circuits before a preamble that dereferences the item can run. Also fixes a latent ASI hazard in the same dispatcher: a delegated handler call (which always starts with `(`) immediately following a statement without a trailing semicolon could get glued onto it (e.g. `const { id, name } = __bfLoopItem` + `(() => …)(__bfEvt)` parsing as `__bfLoopItem(() => …)(__bfEvt)`), throwing at click time for destructured loop params.
