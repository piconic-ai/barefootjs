On Go templates, a TS `number` is now a `float64` everywhere: props, signals, memos, context values, and the fields of named and synthesized structs (loop rows included). It used to be an `int` unless a fractional literal, `.toFixed()` or a fractional caller said otherwise, so an integer literal decided the type: `createSignal(props.b ?? 2)` with `b: 1.5` rendered `1` and a memo `v() * 3` rendered `3` instead of `1.5` and `4.5`; a `{ n = 2 }` default or a prop used only under `%` could not take `7.5` at all (the Go caller did not compile). A `number` read in text or an attribute now prints through `bf_string`, so an integral value prints as JS does (`3`, `1500000`, `1700000000000`), not as `3.0` or `1.5e+06`. A memo whose body is an integer whatever its inputs (`items().length`, `xs()?.length ?? 0`) keeps its `int` field. The runtime helpers that take a JS integer argument (`Slice`, `At`, `Repeat`, `PadStart`, `PadEnd`, `ToFixed`, `Split`'s limit, `StartsWith` / `EndsWith`'s position) now take `any` and read it as `ToIntegerOrInfinity`, so a `float64` field passes through a template call. Go code that builds an `…Input` from an `int` variable needs a `float64(…)` conversion; integer constants assign as before. In `@barefootjs/jsx`, a `BindingScope` row binding now carries its row's type and accessor path (`ScopeBinding.row`), which a backend can give a richer type through `LoopBindingSource.rowType`.
